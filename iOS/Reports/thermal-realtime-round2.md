# 热态实时：第二轮调查（并行调度 + Metal）

测试日期：2026-10-12 22:10–23:00（UTC）。两台设备：iPhone 16 Pro（iPhone17,1，iOS 26.6.2）与 iPhone 14 Pro（iPhone15,2，iOS 27.0）。全部使用同一 Release 构建，档位由启动参数区分。

## 0. 先更正上一轮的一个估算错误

上一轮我给出的判断是"CPU 已经用掉降频后上限的 50–80%，同样的 MAC 数搬到 GPU 估计 5–10 ms，比 CPU 快 5–8 倍"。**这个估算错了，错在低估 CPU：**

| 内核 | Mac CPU | Mac GPU | 16 Pro CPU | 16 Pro GPU | 14 Pro CPU | 14 Pro GPU |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 复数 FIR 2×97 抽头（PAL 709,379 样本） | 0.82 | 0.65 | **1.36** | 4.12 | **1.84** | 4.68 |
| 复数旋转 NCO（同上，均并行） | 0.30–0.43 | 0.44 | **0.38** | 0.94 | **1.02** | 1.31 |
| 功放查表 + 2× 内插 + 抽取 | 1.52 | 0.50 | 2.92 | **1.68** | **3.97** | 5.44 |
| 高斯噪声 | 0.42–0.56 | 0.33 | — | 0.58 | — | 1.24 |

（单位 ms，GPU 侧包含主机写入与读回；误差均在 5e-07 以内，内核数值是正确的。）

实测 CPU 的 FIR 吞吐是 **约 100–170 GMAC/s**，比我假设的 15–25 GMAC/s 高一个数量级——`vDSP_conv` 加 `concurrentPerform` 已经很接近机器上限。所以"CPU 快满了、换 GPU"这个前提不成立。

## 1. 并行 worker 与 QoS 扫描：没有便宜可捡

16 Pro，mobile 档位，8 秒/例，组内热状态一致（S0–S2 均为 fair，S3–S4 均为 serious）：

| 场景 | unlimited (fair) | w4 (fair) | w6 (fair) | qosInteractive (serious) | unlimited (serious) |
| --- | ---: | ---: | ---: | ---: | ---: |
| PAL 默认 | 26.71 (150%) | 29.37 (136%) | 26.90 (149%) | 26.48 (151%) | 26.36 (152%) |
| PAL 损伤 | 35.34 (113%) | 41.85 (96%) | 38.96 (103%) | 38.49 (104%) | 38.42 (104%) |
| NTSC 默认 | 19.16 (174%) | 21.12 (158%) | 18.98 (176%) | 18.89 (177%) | 18.90 (177%) |
| NTSC 损伤 | 24.24 (138%) | 27.36 (122%) | 24.11 (138%) | 23.81 (140%) | 23.86 (140%) |

14 Pro 同样方向：w4 在四个场景分别慢 24.0%、8.5%、3.0%、6.8%，w6 与 unlimited 持平，QoS 无差异。

结论：**worker 数压到 4 会变慢，压到 6 等于不限，QoS 提级无收益**——现在的并行调度已经落在大核上，没有可捡的 10–30%。这一项作为负结果记录，不做改动。

## 2. Metal：两台真机实测后不建议接入

- **复数 FIR 在 GPU 上慢 2.5–3 倍。** 内核是朴素标量实现：每个输出样本从 device 内存读 97 个抽头、做 97 次标量乘加；Mac 的大缓存掩盖了这一点，手机缓存小就暴露了。即使改成 `float4` + 共享内存版本，理论最好也就 1–1.5 ms，与 CPU 的 1.36 ms 持平，因为这条路是访存受限而不是算力受限。
- **NCO 在 GPU 上慢 1.3–2.5 倍**（CPU 侧已是并行区间划分）。
- **只有功放查表真正受益，而且只在 16 Pro 上：1.73 倍**（2.92 → 1.68 ms）；14 Pro 上 GPU 反而慢 1.37 倍（3.97 → 5.44 ms）。
- **噪声**：GPU 0.58/1.24 ms，与已并行的 CPU 版本（Mac 上 0.42–0.56）基本持平。

即使只把功放搬到 GPU，16 Pro 每帧省约 **1.2 ms**（PAL 损伤帧 49.5 ms 的 2.5%），14 Pro 上还是负数。**结论：不值得接入主链路。**

子代理在 Mac 上另外量到两条对架构判断很重要的事实：

- **共享内存不是免费的**：主机↔GPU 实测 71–85 GB/s，一帧 3–4 个平面就是 0.13–0.25 ms 的纯搬运；低算术量的内核（NCO、噪声）基本被这项吃掉。
- **每次 `commit`+`waitUntilCompleted` 只能跑到 GPU 持续吞吐的约 40%**（同一个 FIR 调用：单发 1.37 ms，10 个在飞 0.45 ms）。任何真正的 GPU 集成都必须把整帧各阶段合进一个 command buffer，否则大部分收益在提交/等待上损耗掉。

## 4. 把账算清：瓶颈不在 DSP 核，在管线开销

真机内核测量给出了一个反直觉但很关键的对照。以 16 Pro 的 PAL 损伤帧（49.50 ms）为例，把所有**具名 DSP 核**的实测耗时加起来：

| 具名内核 | 实测 ms（16 Pro） |
| --- | ---: |
| VSB 视觉 2×97 抽头卷积 | 1.36 |
| 接收 IF 4×97 抽头复数卷积 | 2.72 |
| 载波滤波器 2×49 | ~0.7 |
| 功放查表 + 2× 内插 + 抽取 | 2.92 |
| 伴音上采样（13 抽头 × 709k 输出） | ~0.4 |
| 噪声生成 | ~0.6 |
| 同步低通 25 抽头 | ~0.2 |
| 合计 | **约 9 ms** |

而这一帧是 49.50 ms。也就是说**约八成时间不在这些卷积里**，而在：

- 反复的全帧标量校验：`TVChannelIQ.validate()` 的 `i.allSatisfy(\.isFinite)` / `q.allSatisfy(\.isFinite)` 各是一趟 709,379 元素的标量扫描，每帧被调用数次；同类写法还散落在帧与音频路径上。
- 每趟 FIR 都会 `history + input` 复制整个输入（2.8 MB）并把输出数组先清零再全部覆写；一帧约十余次。
- 全帧的标量循环：交叉压缩功率逐格估计、NTSC 基座逐行插入、同步切片与边沿扫描、AGC 探针 `stride().map{}.sorted()`（每帧分配并排序近六千个元素）。
- 每个阶段各自 `concurrentPerform` 起停线程，一帧几十次。
- 各阶段的中间数组分配与清零。

这也正好解释了为什么把内核搬 GPU 没有帮助：GPU 加速的是算力，而这一帧缺的不是算力。同一个 PAL 损伤帧在 M3 Max 上 24.2 ms、在 16 Pro 上 49.5 ms，只差 2.05 倍，而两者的单核算力与核数差距远大于 2 倍——同样指向"相当一部分时间没在算"。

### 修正后的路线

这一节的第一版是从算式推出来的，随后用 Instruments Time Profiler 在真机严重热态下实测，三项被推翻、一项新热点浮出水面。**以 `thermal-profile-14pro.md` 为准**，要点：

| 顺序 | 手段 | 实测依据 | 预计 |
| --- | --- | --- | ---: |
| 1 | 伴音重采样累加链打散（多个部分和 / SIMD4 / vDSP） | 单项最大热点 8.09%，13 抽头依赖加法链 | −4…−6 ms |
| 2 | CVBS 编码与解码内层改 SIMD4/vDSP | 合计 13.4% | −3…−5 ms |
| 3 | 合并零散的 `concurrentPerform` 成少数大并行区 | 并行度只有 2.21×/6 核，串行占比约 55% | −3…−5 ms |
| 4 | 重采样/合并/提取共用一趟搬运 | NCO 1.92% + shift 1.48% + memcpy 1.41% | −1…−2 ms |
| 5 | 20 fps 降档（serious 时视频重复帧、音频不断） | 兜底，覆盖最坏场景 | 产品决策 |

已撤回（实测证明收益只有估计的十分之一或更低）：重设计 97 抽头 FIR（实际只占 1.41%）、向量化 `isFinite` 校验（0.2%）、去掉 FIR 的 `history + input` 复制（<0.5%）。

### 已排除的路线

- **不要把这四类内核搬 GPU**：两台真机实测，FIR 慢 2.5–3 倍、NCO 慢 1.3–2.5 倍，只有 16 Pro 的功放快 1.73 倍（每帧省 1.2 ms，14 Pro 上还是负数）。
- **不要在数值精度上继续省**：能省的单项收益都在毫秒级以下，代价已在第一轮量化为可见的画面误差。
- **不要指望并行调度**：w4 更慢、w6 等于不限、QoS 无差异。
