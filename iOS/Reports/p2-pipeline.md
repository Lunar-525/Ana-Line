# P2：状态有序的跨帧流水线（第一版）

日期：2026-10-12。设备：iPhone 14 Pro（A16，iOS 27.0），mobile 档位，Release，8 秒/例，热状态 serious 对齐。全量回归：见文末。

## 1. 做了什么

### P2-1 状态所有权拆分（行为不变）

`TVUnifiedChannelEngine` 从"一个持有全部状态的结构"改成**门面 + 两条半链**：

| 类型 | 拥有的状态 | 说明 |
| --- | --- | --- |
| `TVTransmitChain` | VSB 调制器、伴音调制器、合并器、RF 信道、两个功放 | CVBS → VSB/伴音 → 功放 → 合并 → 信道 |
| `TVReceiveChain` | 接收机、伴音提取器、解调器、频谱分析 | 一次共享接收 + 视觉检测 + 伴音提取 |
| `TVUnifiedChannelEngine` | `commonGain`、进度账本、策略 | 只做门面与帧边界 |

拆分后**全量 158 项测试 0 失败**（含 P0 的逐位回滚、mobile 档位数值走廊、GUI 实时验收），即信号逐位不变。

### P2-2 二级流水线

新增 `TVFramePipeline`：第 N+1 帧的**发射半链**在流水线线程上运行，同时调用线程运行第 N 帧的**接收半链**，两者重叠而不是相加。

所有权上刻意做了约束，避免"发射任务把流水线本体保活"这类问题：每帧有独立的 `Delivery` 投递对象，发射块只捕获**发射链的 box** 与**该帧的 Delivery**，不捕获流水线本身；因此流水线没有 deinit 工作，且**每次等待都是有界的**（20 秒未完成即抛 `TVError.pipelineStalled`，把"卡住"变成明确报错而不是挂死）。

## 2. 正确性：重叠不得改变任何一个采样

`Tests/AnalogCoreTests/TVFramePipelineTests.swift`（3 项全通过）：

| 测试 | 断言 |
| --- | --- |
| `testPipelineMatchesSequentialExactly` | 与顺序引擎**逐位一致**：视觉 RGB 最大误差 = 0、音频逐采样相等、锁定/行数/载波误差/载波策略/发射遥测全部相等；且 `overlapped ≥ 帧数-2` 证明半链**确实**重叠 |
| `testSharedGainCouplingRefusesOverlap` | 共享增益耦合开启时 `overlapped == 0`，且仍逐位一致 |
| `testCoupledFrameIsRefusedWhileAnotherIsInFlight` | 有帧在飞时提交耦合帧 → `TVError.pipelineCoupling`（响亮失败，而不是悄悄改变 AGC 收敛） |

**唯一的跨帧耦合**（P1 已量出、本轮在代码中确认）：`frontEnd.agcEnabled` 时，第 N+1 帧的发射端要消费第 N 帧接收端测得的 `commonGain`。这种组合下流水线**拒绝重叠**，由调用方停止预取（`allowsLookahead == false`），行为与顺序引擎逐位一致。

## 3. 真机 A/B（交错配对 + 热探针归一化）

顺序与流水线各跑两次，交错进行（pipe → seq → pipe → seq），同一热状态内成对比较：

| 场景 | 流水线 ms | 顺序 ms | 归一化变化 | P95（流水线/顺序） |
| --- | ---: | ---: | ---: | --- |
| PAL 默认 | 28.90 | 31.29 | **−16.0%** | 31.58 / 33.32 |
| PAL 损伤 | 43.05 | 48.66 | **−34.7%** | 51.82 / 54.86 |
| NTSC 默认 | 24.61 | 28.04 | **−14.4%** | 29.12 / 32.00 |
| NTSC 损伤 | 28.63 | 38.08 | **−28.0%** | 32.74 / 39.38 |

两对独立比较（避免跨热态混合）：

| 配对 | PAL 默认 | PAL 损伤 | NTSC 默认 | NTSC 损伤 |
| --- | ---: | ---: | ---: | ---: |
| pipe-a / seq-a | −16.2% | −35.8% | −12.3% | −26.2% |
| pipe-b / seq-b | −15.7% | −33.9% | −15.9% | −29.2% |

**结论：平均 −23%，默认场景 −12…−16%，损伤场景 −26…−36%**，且 P95 同步下降（损伤场景 51.8 vs 54.9 / 32.7 vs 39.4）。这与 P1 用 Signpost 数据算出的上界（发射半链 7.0 ms ∥ 接收半链 16.7 ms，顺序 23.7 ms，即 −30%）**同向同量级**：损伤场景发射半链更重，重叠收益更大。

## 4. 本轮发现并修掉的两个问题

**（1）真机死锁：`deinit` 对自己的队列同步。**
第一版 `TVFramePipeline` 在 `deinit` 里写 `queue.sync {}` 等发射任务结束。但发射块强引用流水线本体——当调用方先释放、发射块随后释放最后一个引用时，**deinit 就会在发射队列自己的线程上执行**，`queue.sync` 变成对自己同步 → 自死锁。真机表现为：报告停在 199 帧（正好第 1 例 8 秒结束处），20 分钟内帧数完全不动，驱动进程空转 21 分钟。
修复：发射块不再捕获流水线本体（只捕获 box + Delivery），deinit 不再需要同步；同时把每次等待改为**有界**（20 秒 → `pipelineStalled`）。修复后同一 A/B 四轮全部正常完成。

**（2）测量错误：把"帧周期"当成了"处理时间"。**
第一版 A/B 我把 `processingMS` 的起点改成了"上一次结束时刻"，于是量到的是**交付间隔（含节流等待）**——两个场景都精确地卡在 40.0/33.4 ms（正好 PAL/NTSC 帧周期），看起来"流水线毫无收益"。是阶段和（default 24.61 ms vs damaged 33.14 ms）暴露了矛盾。改回"本帧工作窗口"后，损伤差值与流水线收益才都显现出来。
教训：**当测量结果恰好等于某个标称值时，先怀疑测量本身**。

## 5. Mac 侧 GUI 实时验收：一次环境性失败（不是本轮改动）

本轮全量回归里 `AnalogGUITests.TVPlaybackTests.testM3MaxMaintainsRealtimeWithPropagationWeatherAndPA` 报过一次失败（NTSC 最差生产帧 42.19 ms > 33.37 ms 预算），单独复现也失败过。判定为**环境性**，证据三条：

1. **超出预算的部分落在与改动无关的阶段。** 失败帧分项 `source_encode_rf_image = [8.28, 5.13, 27.87, 0.89]`，而本轮之前该用例**通过**时是 `[1.74, 3.89, 26.98, 1.14]`——RF 段（27 ms）本来就是最差帧的常态，多出来的 ~7 ms 全在 **FFmpeg 取源**（1.0 → 8.3 ms），这段代码本轮未改。
2. **同一份代码紧接着连跑两次都通过**：PAL 31.3 / 35.9 ms、NTSC 27.3 / 22.9 ms，均在预算内。
3. **机器当时严重争用**：`load averages 12.6 / 12.8 / 13.8`，占用者包括本项目自己的 Mac 应用（`build/ANALINE.app`，已连续运行 4 小时，61% CPU）、`ApplicationsStorageExtension`（88%，磁盘已用 90% 触发系统清理）、WindowServer、Finder 等。

因此做 Mac 侧计时类验收前需要：**退出常驻的 ANALINE Mac 应用**、清理磁盘水位。设备侧（手机）测量不受此影响，因为计时是在手机进程内完成的。

本轮结束时的复跑结果：**AnalogCoreTests 162 项 0 失败**；AnalogGUITests 49 项中同样这一项再失败一次（NTSC 最差帧 36.08 ms vs 33.37 ms 预算，超 2.7 ms），而此时机器 **load average 已升到 23.1**（前一次单独复跑同一代码两次都通过）。这一项在本轮全部改动中都不在关键路径上（流水线与延迟构造只被基准路径使用），判定仍为环境性。

## 6. 把编码也藏进发射阶段（本轮第二轮）

### 诊断

逐阶段对比流水线与顺序（同一轮、热探针归一化）暴露了一件关键事实：

| 阶段 | 流水线 | 顺序 | 归一化 |
| --- | ---: | ---: | ---: |
| modulation | 9.71 | 5.60 | +47% |
| tunerIF | 8.22 | 4.44 | +57% |
| carrierPLL / synchronization / videoDecode | 5.21 / 4.55 / 3.58 | 4.48 / 3.85 / 3.05 | ≈0 |

即：**发射半链（12.1 ms）已被完全藏在接收半链之后** ✓ 流水线确实在工作；而两半并行时彼此的并行阶段因争核而变慢（+47%/+57%），这就是收益小于理论上界的原因。更关键的是算账：

```
帧时间(实测 28.90) ≈ 编码 4.12 + 接收半链 24.55
```

**编码仍在调用方的关键路径上**（"先编码 → 提交 → 等接收"是串行的），而发射侧即使加上编码也只有 16.3 ms，仍小于接收侧的 24.6 ms —— 所以编码完全可以被藏掉。

### 改动与结果

新增 `TVFrameRequest`：把**帧构造（CVBS 编码 + 伴音 PCM）表达为闭包**，由流水线在**发射线程**上执行；调用方关键路径只剩接收半链。校验拆成两处：设置在前台线程校验，音频在发射线程拿到帧后再校验。

| 场景 | 上一版流水线 | 延迟编码后 | 改善 | 相对顺序引擎 |
| --- | ---: | ---: | ---: | ---: |
| PAL 默认 | 28.90 | **23.31** | −19.3% | **−31.5%** |
| PAL 损伤 | 43.05 | **28.75** | −33.2% | **−45.5%** |
| NTSC 默认 | 24.61 | **16.81** | −31.7% | **−27.5%** |
| NTSC 损伤 | 28.63 | **20.41** | −28.7% | **−39.5%** |

**里程碑：在 serious 热状态下，四个场景全部装进帧预算**（PAL 损伤 28.75 < 40，余量 28%；NTSC 损伤 20.41 < 33.37，余量 39%），且都在 14 Pro（A16）上测得。新路径同样有逐位一致测试（`testDeferredConstructionMatchesSequentialExactly`，4 项流水线测试全过）。

### 构建系统教训（排查耗时较长，值得记下）

`swift build --build-tests` **不会**开启 testing 模式，而测试使用 `@testable import`，于是报错。Xcode 构建系统把这个问题报成含糊的 `unable to resolve Swift module dependency to a compatible module`，用 native 构建系统才给出真正的原因 `module 'AnalogCore' was not compiled for testing`。**跑测试请用 `swift test`，不要用 `swift build --build-tests`。**

## 7. 下一步：三段流水线（接收半链再拆）

接收半链内部已做完状态依赖分析，**拆分点合法**：

| 段 | 内容 | 串行墙钟（PAL 默认） | 写入的状态 |
| --- | --- | ---: | --- |
| T | 帧构造 + 调制 + 合并 + 信道 | 7.3（+编码 4.1） | 调制器/功放/信道 |
| R1 | 前端 + 载波估计 + PLL | 15.2 | 前端、载波滤波、相位/频率、跟踪策略 |
| R2 | 检测（陷波/AGC/同步/切片/raster）+ 解码 + 伴音 | 9.4 | AGC（`gain`/`gainDynamics`/`pictureReference`/`clampState`）、同步（`syncLowpass`/`origin`/`period`/misses） |

关键在于 **R2 写入的状态没有任何一项被 R1 读取**（AGC 与同步状态全部在 R2 内写读，R1 只读自己的载波状态），所以"R1(N+1) ∥ R2(N)"不存在反向依赖 ✓。预计帧时间从 23.3 ms 进一步降到 ≈ max(T 16.3, R1 15.2, R2 9.4) ≈ **16 ms 量级**。

## 8. 持续负载验证（180 秒/例，14 Pro，mobile，pipelined + 延迟编码）

短测（8 秒）不足以回答"热起来还能不能实时"，所以跑了 180 秒/例：

| 场景 | 帧数 | 实际 fps | 平均 ms | P95 | 峰值 | 超预算 | 前 1/3 | 后 1/3 | 热状态 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| PAL 默认 | 4498 | **25.0** | 25.81 | 32.21 | 42.92 | 1 (0%) | 23.30 | 30.10 | serious 44% |
| PAL 损伤 | 3367 | 18.7 | **45.48** | 51.16 | 70.36 | 3305 (98%) | 45.85 | 45.52 | serious 100% |
| NTSC 默认 | 5371 | **29.8** | 25.71 | 28.29 | 37.04 | 7 (0%) | 25.57 | 26.26 | serious 100% |
| NTSC 损伤 | 3828 | 21.3 | 33.13 | 37.50 | 49.23 | 1208 (32%) | 31.95 | 34.40 | serious 100% |

结论：

- **默认场景在持续负载下守住了实时**：PAL 25.0 fps、NTSC 29.8 fps，后 1/3 窗口（完全热透）仍在预算内（30.1 / 40 ms，26.3 / 33.37 ms）。
- **损伤场景没有守住**：PAL 损伤稳定在 45.5 ms（预算 40，即 114%），NTSC 损伤 33.1 ms（预算 33.37，正卡在边缘）。注意前/后 1/3 **几乎相同**，说明这不是"跑热了才降频"，而是它在 serious 下的真实成本；8 秒短测得到的 28.75 ms 属于"还没热透"。
- 短测与持续测的差异（PAL 损伤 28.75 → 45.5 ms）说明：**8 秒的 A/B 只能用来做相对比较，不能用来判断"是否实时"**。

**harness 自身的一个缺陷（已修）**：基准每 1 秒保存一次完整报告（含每帧样本，约 17 MB），这份 I/O 不计入 `processingMS`，却实实在在拖低了实际帧率（NTSC 损伤 33.1 ms 本应对应 30 fps，实测 21.3）。已改为每 15 秒保存一次，并复跑验证。这也说明**"实际 fps"与"每帧处理时间"是两个必须分开看的指标**。

**对下一段的判断**：PAL 损伤 45.5 ms 距离 40 ms 差 14%，而三段流水线（接收半链拆分）预计能拿回 20% 左右——这正好是"达标 / 不达标"的区别，所以 P2-5 值得做。

### 保存节奏修复后的复跑（以及一个必须说明的混淆因素）

把报告保存从每 1 秒改成每 15 秒后复跑同一持续测试：

| 场景 | 修复前 平均 ms | 修复后 平均 ms | 修复前 harness 开销/帧 | 修复后 harness 开销/帧 |
| --- | ---: | ---: | ---: | ---: |
| PAL 默认 | 25.81 | 31.76 | — | — |
| PAL 损伤 | 45.48 | 51.04 | — | — |
| NTSC 默认 | 25.71 | 30.15 | — | — |
| NTSC 损伤 | 33.13 | 41.83 | **13.8 ms** | **2.0 ms** |

（harness 开销/帧 = 实际每帧周期 − 每帧处理时间。）

**修复有效**：每帧的 harness 开销从 13.8 ms 降到 2.0 ms，"实际 fps"与"每帧处理时间"终于自洽。但**绝对数值整体变慢了约 20%**，原因是手机在连续数小时压测后已深度降频（两轮持续测试无法绝对比较，同标称 "serious" 内频率仍在下降）。

因此必须明确：**持续测试的绝对数字受设备历史热状态强烈影响（本轮两次相差可达 20%），只有交错 A/B 才是可靠的比较方法**；要做严格的持续对比，两轮之间需要让设备冷却。

在**热透**状态下（后 1/3 窗口）的诚实结论是：默认场景守住实时，损伤场景超出预算约 25–28%（PAL 损伤 52.4 / 40 ms，NTSC 损伤 42.0 / 33.37 ms），这正是三段流水线要吃掉的部分。

## 9. 三段流水线：把接收半链拆开（本轮完成）

### 拆分点与合法性

关键发现让这次拆分成本远低于预期：`TVReceiverFrontEnd` **本身就是独立结构**，而 `detect(_ front: TVFrontEndOutput, …)` **已经把前端输出当参数接收**，内部从不访问 `self.frontEnd`（已逐一核对）。于是把它拆成两个独立状态所有者即可：

| 级 | 类型 | 拥有的状态 |
| --- | --- | --- |
| R1 前端 | `TVFrontEndStage` | 调谐相位、共用 IF 滤波器、输入/IF 非线性级、频谱 |
| R2 检测 | `TVDetectStage` | 载波滤波与估计、PLL、AGC、同步、切片、raster、解码、伴音提取 |

依赖是单向的（R1 → R2），**R2 写的状态没有任何一项被 R1 读**，因此"R1(N+1) ∥ R2(N)"合法。唯一的跨帧耦合仍是共享增益，已有 `pipelineCoupling` 拒绝机制覆盖。

`TerrestrialReceiver` 保留自己的前端供遗留入口使用，并新增 `receiveDetected(_:settings:started:)`，让拥有前端的调用方直接进入检测。`TVReceiveChain` 退化为门面，顺序路径行为不变——**指纹测试逐位通过**。

### 真机结果（交错两对，热探针归一化，8 秒/例）

| 场景 | 顺序 | 三段流水线 | 归一化 | 三段 P95 |
| --- | ---: | ---: | ---: | ---: |
| PAL 默认 | 30.10 | **20.14** | **−50.4%** | 23.12 |
| PAL 损伤 | 39.19 | **21.42** | **−61.1%** | 23.07 |
| NTSC 默认 | 22.17 | **14.76** | −46.1% | 15.97 |
| NTSC 损伤 | 27.67 | **15.14** | −55.4% | 16.19 |

相对上一版（二级 + 延迟编码）又提升 **12–26%**，相对顺序引擎平均 **−53%**。

### 顺带修掉的一个真实析构陷阱（真机崩溃根因）

第一版三段流水线上真机后**在第一例结束处崩溃**（报告停在 199 帧、`startedAt` 不再更新）。本地用"用例切换"场景复现，拿到栈：

```
_dispatch_semaphore_dispose.cold.1   ← libdispatch 陷阱
TVFramePipeline.deinit
```

原因：一次运行结束时**还有帧在飞**（用例按时长结束、播放器 seek），那次提交取走的信号量许可永远不会被 `receive()` 归还；libdispatch 在信号量**被销毁时若许可已被取走**（`value < orig`）会直接 trap。修复：析构时按 `inFlight` 把许可还回去。已固化为永久回归测试 `testTeardownWithFramesInFlightIsSafe`（三个用例切换、每个都留一帧在飞）。

这个 bug 在二级流水线版本里就已经潜伏（只是释放时机凑巧没触发），三段版本让它稳定复现。

### 三段流水线的持续负载验证（180 秒/例）

与二级流水线的持续测对比，用与改动无关的阶段（解码+同步）做热探针归一化（设备历史热状态差异很大，因子 0.868–1.134）：

| 场景 | 二级 平均 ms | 三段 平均 ms | 热因子 | 归一化变化 | 三段实际 fps | 预算 | 达标 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| PAL 默认 | 31.76 | **26.20** | 1.134 | −27.3% | **25.0** | 40 | ✓ |
| PAL 损伤 | 51.04 | 48.98 | 1.133 | −15.3% | 19.8 | 40 | ✗ 122% |
| NTSC 默认 | 30.15 | **19.38** | 0.868 | −26.0% | **30.0** | 33.37 | ✓ |
| NTSC 损伤 | 41.83 | **31.91** | 0.957 | −20.3% | **29.4** | 33.37 | ✓ |

**四个场景中三个在持续热透下守住实时**（PAL 默认后 1/3 窗口 31.9 / 40，NTSC 默认 19.0，NTSC 损伤 31.6 / 33.37）；只剩 **PAL 损伤** 49.0 ms / 40 ms（超 22%）。

值得注意的对照：爆发（8 秒）A/B 里 PAL 损伤收益最大（−61%），持续测里收益最小（−15%）。原因是深度降频后**受限于 CPU 总量**，而流水线只是把"等待"换成"并行"，不能凭空造出算力。PAL 损伤恰恰是**工作量最大**的场景（发射端双功放 + 耦合估计 + 信道分数延迟回声 + 雨衰噪声）。所以剩下的缺口是**工作量**问题，不是调度问题。

### 三段流水线在 Mac GUI 验收上的一个待判定项

全量回归里 `AnalogGUITests.TVPlaybackTests` 的两项实时验收在本轮末失败（PAL 最差帧 39.99 / 40 ms，NTSC 36.02 / 33.37 ms）。注意其数字特征：PAL 的"最差帧"几乎正好等于帧周期（40 ms），说明这个指标包含**等待节拍**的时间，对整机争用极其敏感（当时 load ≈ 7，且本项目的 Mac 应用常驻）。

GUI 走的是 `.full` 档位，因此本轮所有 mobile 专属优化（含载波三级策略）在 GUI 路径上**不生效**；真正作用于 GUI 路径的只有 P0 的原子提交、发/收链拆分、`uninitializedFloats` 与重采样器的 4 路展开。其中重采样器展开在 Mac 微基准上就是"PAL 略快、NTSC 略慢"的中性项。

为此在 `5b5a0c2`（P0 之前）的独立 worktree 上做了严格 A/B。**结论：不是回归。**

最有说服力的证据不是"最差单帧"（那是 ~150 帧的极值统计，且指标包含节拍等待与 FFmpeg 取源），而是**两棵树同时运行**、在相同机器负载下测得的顺序路径**每帧平均耗时**：

| 制式 | 基线 5b5a0c2 | 当前 | 变化 |
| --- | ---: | ---: | ---: |
| PAL-D/K | 29.13 ms | **25.65 ms** | **−12.0%** |
| NTSC-M | 20.02 ms | **19.28 ms** | **−3.7%** |

（场景为 GUI 同款损伤设置、`.full` 档位、各 20 帧求均值。）

失败运行的 `production_deadline_misses` 只有 **1/166**，且其 `worst_frame_source_encode_rf_image_ms` 中 FFmpeg 取源为 **4.34 ms**（基线同项 0.96–1.04 ms）——多出的 3.4 ms 全部落在本轮未改动的 FFmpeg 解码上。因此这两项用例的失败是**极端值统计遇到整机争用**，不是代码回归。

附带测得：P0 的原子提交本身约 **0.61 ms/帧**（PAL、full 档、最大损伤），代价真实但很小，暂不优化。

## 10. 工作量削减的第一次尝试（结论：编译器已经做掉了）

用户批准"放开最后几位换性能"后，先按剖析热点做了两次尝试，结果都是**零收益**，值得记录以免重复走：

| 尝试 | 结果 | 结论 |
| --- | --- | --- |
| 重采样抽头和的 SIMD4 化（保持 lane 分配与折叠顺序不变） | **逐位一致 ✓**，PAL 25.67→25.71（噪声），NTSC 18.59→18.62（另一轮 −3.6%） | LLVM 早已把 4 累加器循环自动向量化；该内核是 **L1 载入吞吐受限**（46 倍上采样下每个输出读 51 个输入样本 × I/Q），不是乘加吞吐 |
| `encode` 逐样本 Double 位置映射改为按 (宽度, 行长) 缓存 | 逐位一致 ✓，但 **25.67→25.71 无变化** | 编译器已做等价优化；该缓存零收益又增加状态，**已撤销** |

同时纠正了一个我自己的猜测：视觉载波 `carrier()` **本来就是 4 相位精确查表**（4fsc 约定，fs/4），并不存在逐样本 `sin/cos`。剖析里的 `VVSINCOSF` 来自伴音 FM 合成，`VVLOGF` 来自噪声/雨衰。

**因此：帧时间已到"工作量"瓶颈，而工作量分散在长尾内核上**（重采样 11%、CVBS 编解码 ~12%、功放 3.4%、信道 3%、伴音 NCO 1.9%、校验 1.5%…）。下一个真正有量的杠杆是**伴音上采样的两级化**（384 kHz→17.73 MHz 的 46 倍上采样目前用 51 抽头直接内插，两级级联可把 72M 次乘加降到约 13M，估计 −7…9% CPU）。这是滤波器设计变更（估计值会变、需用频谱验证镜像抑制不退化），留作下一轮的第一件事。

另外一个必须记住的测试环境事实：**GUI 的两项实时验收只在冷机、安静时才有效**。它们断言 5 秒播放里的**最差单帧**（指标还包含节拍等待与 FFmpeg 取源）；在全量回归里（前面刚跑过大量 DSP 测试、机器已热）它们会失败，而单独运行同一份代码则通过。同机 A/B 已证明顺序路径比改动前**快 4–12%**，所以这不是代码问题，而是这两项测试的设计前提（冷机）没有得到满足。
