# 把帧流水线移植到 macOS 渲染器

日期：2026-10-12。目标：让 macOS 的 `TVRenderer`（GUI 与 `TVPlaybackTests` 走的路径）也吃到三段流水线，同时**不改变任何画面内容**、不破坏 seek / 暂停重渲染 / 预热语义。

## 1. 与前两层的区别

| 层 | 改动量 | 效果（实测） |
| --- | --- | --- |
| 结构性（AnalogCore） | 零改动 | 顺序路径 −4…−12% |
| `.mobile` 档位 | 一行/一个开关 | −16…−19%（不再逐位一致） |
| **流水线（本次）** | 改 `TVRenderer` | **生产帧 −28…−33%** |

## 2. 收益形态与手机不同（重要）

`TVRenderer` 是 **"每次调用返回一帧"** 的模型，所以不能像手机基准那样背靠背重叠。移植后的形态是：

```
调用 N:  [接收 N]（N 的构造+发射+前端已在调用 N-1 结束时提交，故已基本完成）
         → 生成预览图 → 返回
         → 在此之后的帧间空隙里：构造/发射/前端 帧 N+1
```

也就是说**发射+前端（约 11–15 ms）被移出调用的关键路径**，挪进调用返回后的帧间空隙；调用内部只剩 **检测 + 图像转换**。这也解释了 GUI 验收测试里"取源 0.005 ms、编码 1.2 ms"的读数——它们已经不在被测窗口里了。

## 3. 实现

- 渲染器持有 `TVFramePipeline` 与一个 `prepared`（下一帧的像素、源图、伴音、编码计时）。
- 每次渲染：若 `prepared` 命中当前帧 → **不再读解码管道、不再重复 RGB 转换**，直接 `receive()`；否则正常取帧并提交。
- 提交通过 `TVFrameRequest` 闭包把 **CVBS 编码放到发射线程**（顺带在那里测量编码时间，用一把小锁交回）。
- 取帧逻辑抽成 `readSourceFrame`，**seek/跳转时重启解码管道的行为与原来完全一致**。
- `endPlayback()` / `selectStandard()` 一并丢弃流水线与预取帧。

### 语义保持不变的三条规则

1. **重建流水线的条件与原来一致**：帧序不连续、或 `seed` 变化、或**预取帧与本次请求不是同一帧**。（后者必然意味着不连续。）
2. **普通设置变化不重建**。GUI 每帧都传 `buffer.settings`，拖动滑块时每帧都在变；若此时重建，接收机每帧都会重新捕获，画面会持续闪动 ✗。因此沿用原语义（接收机状态跨设置变化保留），代价是**发射/前端侧滞后一帧**——这不可见，且检测侧用的是新设置。
3. **预取失败不污染流**。读到片尾、取消、管道错误都在 `submit` 之前发生，因此不留任何"在飞"的帧；下一次调用照常取帧。若 `submit` 本身抛错，同样未入队。

## 4. 验证

`TVRendererTests` **11 项全部通过**，含 seek、稳态播放、持续实时、读管道重启。其中：

| 测试 | 移植前 | 移植后 |
| --- | ---: | ---: |
| `testRickrollPropagationWeatherAndPARealtimeProfile` | 104.5 s | **72.1 s（−31%）** |

（该测试渲染固定帧序列，耗时直接反映每帧延迟。）

GUI 验收 `testM3MaxMaintainsNormalSpeedAndContinuousAudioForBothStandards`（同机）：

| 指标 | 基线 | 移植前（近期，机器较热） | 移植后 |
| --- | ---: | ---: | ---: |
| PAL 最差生产帧 | 33.77 ms | 39.99 ms | **24.23 ms（−28%）** |
| NTSC 最差生产帧 | 26.31 ms | 36.02 ms | **17.75 ms（−33%）** |
| deadline miss | 0 | 0–1 | **0 / 0** |
| 呈现帧数 | 139 / 167 | 139 / 167 | 139 / 167（实时不变） |
| 欠载采样 | 0 | 0 | 0（伴音完好） |

**副产物**：这两项 GUI 验收从此不再卡在预算边缘，之前那种"整机一忙就失败"的脆弱性明显缓解。恢复移植后复跑一次，四项通过用例的 `maximum_production_ms` 为 **22.09 / 19.10 / 23.48 / 19.68 ms**（预算 40 / 33.37），全部 `skipped_frames = 0`、`underrun_samples = 0`。

最终回归：**AnalogCoreTests 165 项 0 失败，其中 `TVRendererTests` 11/11 全过**（含 seek、稳态播放、持续实时、读管道重启）。剩余的 GUI 失败全部是负载/热敏感的验收项，已在本节说明其环境成因。

## 5. 已知的度量口径变化（诊断用，不影响断言）

- `Preview.encodeSeconds` 现在来自**发射线程**实测的编码时间；`decodeSeconds` 只覆盖 `receive()`（预取已把发射/前端移出）；`prerollSeconds` 覆盖预热提交与接收。
- 阶段遥测（`timings.channel` 等）现在测的是**流水线线程上的跨度**，因此可能包含调度延迟（实测出现过一次 231 ms 的单帧极值，落在帧间空隙里，不影响 `maximum_production_ms`）。这些量只用于诊断，不参与断言。

## 6. 一次误判与纠正（值得记录）

移植完成后跑全量回归，`testM3MaxPresentationSurvivesProducerStalls`（故意每 60 帧注入 120 ms 生产者停顿，断言呈现不被打断）失败。我最初判断是移植引入的回归，于是**撤回了整个移植**——撤回后该测试**仍然失败**，这才发现原因在别处：

同一台机器上，**未改动的代码连续 3 次都失败**（负载仅 5.0），而且它的表现比移植版**更差**：

| 指标 | 原版（未移植） | 移植版 |
| --- | ---: | ---: |
| PAL 掉帧 / 欠载采样 | — / 6384–6504 | **0 / 2196** |
| NTSC 掉帧 / 欠载采样 | 7 / 24380 | **5 / 22764** |
| NTSC 呈现间隔上限 | 102 ms | **71 ms** |

对照分项可以看到环境原因：该测试的最差帧里 **RF 段 = 31.3 ms**，而一小时前该全量回归通过时是 27–29 ms —— **这台 Mac 现在比当时慢约 15%**，足以把这个边缘测试压过去（它的预算只有 1.5 帧）。这与本会话在设备侧反复观察到的热漂移是同一类现象。

教训：**跨时间比较测试结果时，先确认未改动代码在当前机器状态下的表现**。撤回是对的纪律（不能带回归交付），但判断错了原因。
