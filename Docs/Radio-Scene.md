# 共享无线电场景

Radio 页面只有共享无线电环境：**固定 8 个 TX 和 2 个 RX**，配置彼此独立。TX 槽位常驻，不提供添加或移除——每台自带电源键，开关就是让它上/下频道的方式。TX 选择调制方式，RX 选择解调方式，均支持 AM、FM、USB、LSB、CW、PM，允许故意错配来比较接收效果。原先的“单台收发”页面已移除，五种模式的核心仍保留在 `AnalogCore`，见 [Radio 调制 / 解调核心](Radio-FM.md)。

## 操作

- 上方 8 个 TX 槽横向排列，每台独立一列，槽位数固定。每台频谱以频率为纵轴、功率为横轴；刻度范围 ±384 kHz、−100 至 +16 dB，横向为对数功率。填充轮廓取自真实 FFT 测量，阴影带为当前调制方式的占用带宽，虚线为载波位置，右缘三角标记峰值。频率统一相对环境基准载波，发射功率相对单位载波驱动。启动时八台全部就位：载波以基准载波为中心、间隔 60 kHz 展开（−180 至 +240 kHz），测试音依次为 440 / 550 / … / 1210 Hz，所以不用动任何旋钮就能在 RF 全景里分辨八台。标题栏显示的是**通电台数**而不是总数。
- 拖动 TX 频谱改变载波位置，旋钮精调；电源键可单独开关。底部音源 / 参数按钮可导入独立音频或使用不同频率的测试音。音频自动循环；CW 使用独立 Morse 文本和速度。
- RX 沿用地面电视的同一套仪器：相同的真实 FFT 测量、`TVSpectrumHistory` 瀑布图、LCD 像素面、屏面色板、0 / −100 dB 与“现在 / −10 s”标尺以及色阶图例。频率为横轴、时间向下，最新一行在顶部，窗口为 10 秒；顶部显示可用带宽与实测 RBW。显示调谐后、解调 IF 前的窄带 I/Q；阴影与括号标出本机 IF / 边带，虚线为调谐位置。点击或拖动瀑布图调谐。
- RX1 / RX2 右侧的“无线电环境”面板显示该接收机前端在调谐前的宽带 RF：全部 TX 载波、环境噪声与过载。频率覆盖 ±384 kHz，可用 ×1 / ×2 / ×4 / ×8 缩放（缩放时裁剪像素栅格而不是放大像素），放大后拖动平移；标题下方列出所选 RX 的开关、位置、调谐与解调方式。
- 两个瀑布图共用同一套场景标记：T1–T8 为发射台载波（颜色与上方 TX 卡片一致，关机后转为暗色虚线，标签重叠时自动分行堆叠），R1 / R2 为两台接收机的调谐位置；括号标出各自的 IF / 边带通带（USB / LSB 为单边带），本机括号加粗高亮，被选为环境面板数据源的接收机同样高亮。窄带瀑布图只显示落在其带宽内的发射台，可直接观察邻频台进入通带的过程。
- RX 解调方式与 TX 无关联。音频带宽 / 边带带宽 / CW 接收带宽、RF 增益和位置可独立调整；服务面板还能设定频偏、相偏、加重、AM 调制度标定、CW BFO 和前端过载。每台 RX 的解调输出电平（dBFS）、21.33 ms 音频包络与削顶指示实时显示，方便直接对照串台造成的差拍与衰落。
- `RX 1` / `RX 2` 单独监听对应接收机，`L / R` 将两台送到左右声道；只有一个 RX 时复制到两侧。共享的双声道音频回调保证同一时间轴。监听音量不修改 RF 信号。
- 演示场景包含近频串台、邻频选择性和 FM 同频捕获。每个场景都只比较两台，做法是把另外六台**断电**而不是删除：槽位保持八个，场景只是同一批槽位的一种配置，因此随时可以用电源键把其他台重新开起来。点击启动后无需生成缓存；运行中可开关设备并修改参数。八台全关时可观察背景噪声；启动播放需要至少一个 RX。

## RF 链路

每台 TX 的 48 kHz PCM / CW 键控源 → 独立调制 → 带限升采样至 768 kHz → 连续 NCO 搬频 → 独立功率 / 电源平滑 → 按 TX–RX 距离计算路径 → 每个 RX 线性合成所有 TX → 加环境噪声 → RF 增益 / 可选过载 → 独立连续调谐 → 带限降采样 → IF 与选定解调 → 音频。

串台来自解调前的复数 RF 叠加，不混合已解调音频来伪造串台。即使两台 AM 输入音频均为零，相近载波也会在包络检波时产生差频啸叫。FM 强弱台的竞争由叠加后的相位及限幅鉴频产生。

位置为一维 km 坐标；场强按 1/r 衰减，在 1 km 处归一化，小于 0.25 km 时限制增益。传播延迟及基准载波相位随距离变化。每条路径使用 33-tap 窗口 sinc 分数延迟，统一增加 16 个 RF 样本的因果延迟，避免简单线性插值削弱高频偏移台。单个反射路径具有可调场强和额外延迟，按载波相位与 I/Q 延迟相干叠加，产生衰落。每个 RX 的噪声流独立且可重复。可选 RF 放大器直接复用电视前端的幅度压缩与 AM-PM 模型。

收发基准采样率固定 48 kHz，内部各调制模式使用 96 / 192 / 384 kHz，再与共同 768 kHz 网格转换。频率偏移限制 ±250 kHz，并校验占用带宽留在共享网格内。显示频谱为实际 RF / 调谐 I/Q FFT，约 85 ms 刷新；瀑布图沿用 100 ms 时间桶。

每块 1024 个音频样本（21.33 ms）。DSP 在后台 actor 计算，双声道回调只消费有限 PCM FIFO。暂停冻结场景时间；重置时间清空 RX 历史。暂停后恢复时重建 DSP，文件 / 测试音继续场景时间轴，CW 消息重新开始。参数改变可能出现短暂收发与滤波过渡。迟到音频丢弃并以静音补位，欠载计数显示在底部。

## 实时管线

音频与 GUI 的关键路径都不经过 MainActor：

```
Audio source preparation  →  Dedicated DSP producer  →  Bounded audio FIFO  →  Core Audio callback
                                       ↑                           ↑
MainActor ──► 参数快照（快照锁）          └────── 直接写入 ────────────┘
MainActor ◄── 状态 / 统计信息（50 ms 轮询）
```

DSP 与生产循环跑在专用 `DispatchQueue`（`.userInteractive`，串行），不再共用协作线程池：协作池的线程数等于 CPU 核心数，一块 6 ms 的 DSP 计算会占住一条线程，把同一进程里其他 Task（包括音频生成）一起拖慢，GUI 随之掉帧。参数通过快照盒（`RadioSceneStateBox`）下发，DSP 完成后直接写 FIFO，不跨主线程边界。

参数盒的显示对象（TX 频谱、RX 瀑布图）按需创建，生产者与视图始终拿到同一个对象；显示发布发生在生产者队列，SwiftUI 在主线程 coalesce 重绘。

状态栏实时显示四项指标，用来区分计算、调度和缓冲：

- **DSP** —— 单块计算耗时（8 FM TX / 2 FM RX 约 10.7 ms）。
- **调度** —— 从需要一块数据到它进入 FIFO 的端到端耗时，含排队等待；它与 DSP 的差值就是调度延迟（实测约 0.06 ms）。仅看 DSP 无法解释欠载：假设生产被调度延迟压到 18 ms，18 + 6 仍会超过 21.33 ms 的块预算。
- **FIFO** —— 生产期间的最低水位；归零意味着声卡回调找不到数据，与 DSP 多快无关。
- **欠载** —— Core Audio 回调的补零次数。

声卡回调只消费 FIFO，不执行调制 / 解调，也不等待网络或磁盘。FIFO 是预分配的 **SPSC 环形缓冲**：生产者持有写计数、回调持有读计数，双方用 C11 原子（acquire / release）同步，**回调里既没有互斥锁也没有分配**，因此不存在优先级反转——早先的互斥锁会让被抢占的生产线程把高优先级的回调一起拖住。读取是固定上限的内存拷贝，不足时补零。环形索引与时间轴计数分开：短读只推进环，时间轴仍按完整请求前进，所以生产者停顿表现为静音而不是让后面的声音整体前移。

生产者带**背压**：环形缓冲没有空间时不跑 DSP，只等回调排空。此前生产者不看余量一路狂跑，填满缓冲后 `append` 抛错、生产者随即退出——这正是「TX 少、DSP 快反而更卡」的原因：DSP 越快缓冲越早填满，生产者越早死掉，之后全是静音。现在 2 秒的运行里生产者稳定产出 100+ 块、欠载为零。

## 显示快照与失效范围

可视化走「DSP 产数据 → 线程安全快照 → MainActor 定时器 20 Hz → SwiftUI」：

```
AsyncAlter DSP ──► 计算频谱/波形 ──► Display Snapshot（只保留最新）
                                        │ 线程安全交换
                              MainActor UI Timer 20 Hz
                                        │
                                  SwiftUI Observable ──► View Render
```

DSP 只负责把可视化数据**渲染好并存进快照**，从不通知 SwiftUI、也从不等 MainActor。MainActor 按自己的节奏在 20 Hz 上发布最新一帧；GUI 一时处理不过来就丢掉旧的可视化帧，不排队堆积几十个更新任务——音频必须连续，频谱少画一帧完全不可见。此前每个音频块都发一次失效（56 Hz），8 个 TX 频谱 + 2 路瀑布图各自排队，现在整幅重绘降到约 1.3 ms。

**失效范围**是另一条独立的约束。`ObservableObject` 的订阅是**对象级**的：`settings` 一旦是 model 上的 `@Published`，拖一个旋钮就会重建 `RadioSceneView`、全部 TX 卡、全部频谱和两路瀑布图——实测一次旋钮动作 14–17 ms，直接打爆 16.7 ms 帧预算。现在 `settings` 不发布，每个电台有自己的 `RadioSceneStationSignal`，旋钮只失效自己那张卡（`scene=0 card=1`，约 4 ms），而且与 TX 数量无关。全局环境旋钮（噪声底、反射、基准载波）会移动所有标记，走 `edit` 做场景级刷新。

`RadioSceneInvalidationTests` 把这条守成回归：一次旋钮动作**不得**重建场景、必须且只能重绘被编辑的那张卡。

## 交互预算

播放循环每 3 ms 检查一次 FIFO，但**界面时钟只在 50 ms 边界发布**（约 20 Hz），播放按钮和时间读数各自作为独立视图观察时钟，主控条（音量旋钮、监听选择、按钮）不随之重建。整幅重绘（8 TX 频谱 + 2 RX 瀑布图 + 环境面板）控制在 3 ms 内，约每 85 ms 一次。

解码后的 PCM 只在**被改动时**推送给 DSP actor（按 `sourcesRevision` 比较），不再每块跨边界传递整个 clip 字典；循环音源用顺序读取（一次边界检查、无逐样本取模）。TX 频谱轮廓在测量到达时一次性算好（160 行），不在渲染阶段切 2048 个 bin；原生旋钮只在数值真正变化时重绘。

`swift test -c release --filter RadioScenePerformanceTests` 覆盖交互预算与实时管线：整幅重绘上界、时钟发布频率、“导入音频与测试音同价”，以及调度延迟 / FIFO 水位 / 欠载三项实时指标。

这是有限带宽内的模拟无线电环境，不是电磁场求解器；没有模拟天线方向图、移动多普勒、电离层、多阶反射或真实硬件设备。功率是相对参考，不是绝对发射瓦数 / 接收 dBm。当前场景配置在页面会话中保持，尚未提供场景文件保存、多 RX 录音或 WAV 导出。

## 快速触摸板滚动验收（2026-10-14）

默认窗口拖动改为标题栏空白处的原生 `NSView` 调用 `NSWindow.performDrag(with:)`，按钮保留自己的命中区域。整窗背景拖动关闭；SwiftUI `WindowDragGesture` 仅留作显式 `ANALINE_DRAG=gesture` 对照，默认使用 native。窗口透明（玻璃）效果目前**默认关闭**：它要求 `window.isOpaque == false`，而这正是让 AppKit 每个显示周期重建窗口不透明区域、把主线程拖到 40% 的原因。关闭后窗口自绘纯黑底，标题栏空白处的原生拖动表面保持不变。`ANALINE_GLASS=1` 可以不加编译把玻璃效果放回来，与 `ANALINE_DRAG` 是同一套 A/B 方式。

`swift test -c release --filter TXBoundaryProbe` 在同一构建中比较 gesture / none / native，覆盖 8 TX 和 2 RX 的实时播放。测试将连续像素 `NSEvent` 直接送入真实 `NSScrollView`：约 25 ms 的大幅输入，接约 350 ms 指数衰减的 momentum 事件，三次交替方向甩动。事件带单调递增时间戳，正确设置手指与惯性开始／改变／结束阶段。实际滚动范围必须超过 300 pt，累计位移和惯性位移均有断言；不再通过直接设置滚动位置测空操作。

本机这一轮默认 native 的结果（当时还能按 6 / 7 / 8 台扫描，现在槽位固定为八，这一维已经消失；表里的数字作为历史记录保留）：

| TX / RX | 滚动范围 | 三次累计位移 | 惯性位移 | 输入间隔 P95 | 欠载样本 |
| --- | --- | --- | --- | --- | --- |
| 6 / 2 | 493 pt | 2105 pt | 1134 pt | 10.34 ms | 0 |
| 7 / 2 | 493 pt | 2110 pt | 983 pt | 10.55 ms | 0 |
| 8 / 2 | 493 pt | 2072 pt | 1241 pt | 10.32 ms | 0 |

累计位移包含边缘回弹。三种拖动方案在这轮输入间隔上的差异不大，不能据此声称拖动区域计算是全部卡顿的原因。这里记录的是合成触摸板事件的处理与主线程输入节奏，不是物理触摸板、屏幕呈现时间或 GPU 帧率测量。

重绘测试补上 `apply` 后的 `publish`，确保统计的是真实失效后的绘制：8 TX / 2 RX 平均 3.53 ms；单旋钮动作通电 2 台时 3.82 ms、通电 8 台时 2.98 ms，两者都只重建一张卡。相关 Release 回归 24 项，22 项通过、2 项按默认设置跳过可选的原生控件截图检查；满载 FM DSP 10.51 ms、端到端块耗时 10.53 ms、欠载为零。（最初扫描的是 2 / 8 个**槽位**；槽位固定为八之后，同一测试改为扫描通电台数，结论不变：单旋钮只失效一张卡。）

### 完整应用复测

完整的 `build/AnaLine.app` 也有显式诊断入口：设置 `ANALINE_TOOL=radio`、`ANALINE_RADIO_TX=6`、`ANALINE_RADIO_MUTE=1`、`ANALINE_SCROLL=1` 后启动。它运行完整 `ContentView`，保留标题栏和实时音频，对同一套八台配置重复甩动。`ANALINE_RADIO_TX=N` 现在是**给前 N 台通电**（不再改变槽位数），`ANALINE_SCROLL_ROUNDS=N` 设定重复轮数，默认 2 轮、上限 20。固定窗口请求 1100 × 760，实际滚动范围约 543 pt；不强制同步绘制，观察应用正常运行循环的刷新回调。普通启动不执行诊断。

注意：滚动范围由八个常驻卡片的高度决定，已经与开通台数无关，所以早期“满槽位转六台”这一类对比无法再复现。

完整应用采样发现 TX 频谱中固定刻度文字反复排版，已把每台五个固定标签移出实时 Canvas，交给保留的 Text 视图；频谱、载波拖动和玻璃效果保留。诊断模式参数改为大小写无关，修复注释要求 `radio` 而实现只接受 `Radio` 的不一致。

[初步完整应用记录](Benchmarks/Radio-full-app-scroll-2026-10-14.txt) 保留全部轮次，包括被遮挡的无效数据。第二轮结束时前台可见的 6 / 7 / 8 TX，刷新间隔 P95 为 11.16 / 10.38 / 9.70 ms，最大为 17.44 / 17.11 / 18.64 ms，欠载为零。但这轮只在每组末尾检查前台状态，不能认证全过程可见。最新诊断已增加激活稳定等待及逐事件遮挡检查；未满足前台条件时明确中止，不把后台降频记作 Radio 性能结论。
